# Case 6 — V1 — "brake pads" (ambiguous)

- **Case ID:** case-6
- **Variant:** V1 (rubber-stamp Verify)
- **Query:** `brake pads` (NO qualifier — deliberately under-specified)
- **Expected:** ASK_QUESTION (refusal/clarification trigger)
- **Failure class:** refusal/clarification trigger — tests Triage's ASK path

This trace documents the architecture's intended behaviour on a 2-token under-specified query that lives in at least three plausible chapters. The expected outcome is **not** a code — it is a multiple-choice clarifying question generated by Triage with a Q-budget of max 2 questions per session.

---

## Stage 1 — TRIAGE (Gemini 2.5 Flash, json_schema)

### Reasoning

The query is `brake pads`. Triage's job is (a) extract attributes, (b) decide CLASSIFY vs ASK vs REFUSE, (c) propose candidate chapters if classifying or an MCQ if asking.

What Triage actually has to work with:
- `material` — UNKNOWN (could be asbestos-based, ceramic, semi-metallic, organic, sintered metal)
- `form` — "pads" (article form)
- `function` — "braking / friction" (clear)
- `intended_use` — UNKNOWN (the trap: motor vehicle? motorcycle/bicycle? industrial machinery? railway? aircraft? press brake — different meaning entirely?)
- `processing_state` — N/A
- `composition` — UNKNOWN

Three plausible chapters surface from the description data (evidence below in Stage 2):

| Chapter | Heading | Why brake pads land here |
|---|---|---|
| **68** | 6813 | Friction material AND ARTICLES THEREOF (sheets, rolls, **pads**) for brakes — the material/article-itself classification |
| **87** | 8708 | Parts and accessories of motor vehicles (8701-8705): "Brakes and servo-brakes; parts thereof" |
| **87** | 8714 | Parts and accessories of motorcycles/bicycles (8711-8713) |
| **84** | (various) | Industrial machinery brakes (e.g., for cranes, presses, hoists) — parts under the parent machine heading per Section XVI Note 2 |

This is **textbook GIR 1 ambiguity**. GIR 1 says classify by terms of headings and any relative Section/Chapter Notes. Multiple headings legitimately cover "brake pads" depending on end-use and material. Without disambiguation, the pipeline cannot apply GIR 1 deterministically and would have to fall back to GIR 3 — which itself requires knowing whether the article is "presented as parts" of a specific machine.

Specifically: a friction pad **not yet mounted** and sold as a friction-material article goes to **6813** by the heading's own text. A friction pad **identifiable as a part of a motor vehicle** goes to **8708.30** by Ch.87 Note 2(e). Same physical object, different classification. The deciding fact is **intended use at importation/exportation**, which the query does not state.

Completeness score: **~0.25** (form present; material, intended_use, composition all missing). Well below the 0.50 threshold that Stage 0 of the legacy specificity-analyzer used.

Triage's correct decision is therefore **ASK** with a multiple-choice question that disambiguates the deciding fact (intended_use / vehicle-type), not material — because the material question (asbestos vs non-asbestos) only matters AFTER we know we're in Ch.68; if it's a motor-vehicle part, GIR 1 sends us to 8708 regardless of material per Note 2.

### Why ASK and not REFUSE

REFUSE is reserved for queries that have **no plausible HS classification at all** (e.g., "moon rocks for research"). "brake pads" has the opposite problem — too many plausible classifications. ASK is the correct lever.

### Why ASK and not CLASSIFY-with-low-confidence

The existing legacy rule `vehicle_parts_function` in `backend/src/rules/chapter-rules.ts:113-145` would currently match on the keyword `brake` alone and force Ch.87 at priority 100. **This is a diagnosed bug** — exactly the kind of spurious-keyword routing the Phase 3 rebuild is meant to remove. Phase 3 Triage must require *intended_use* evidence (the word "vehicle"/"car"/"truck"/"motorcycle" etc.) before committing to Ch.87, not the mere presence of the friction-component word "brake".

### Q-budget

Per spec: max 2 questions per session. After ASK #1 (intended_use), if the user picks `motor_vehicle` we have enough to proceed to Stages 2-4. If the user picks `friction_material_only`, we still need to ask material (asbestos vs not, since 6813.20 vs 6813.81 splits on that) — that would be ASK #2, exhausting the budget. After that, the pipeline must commit or escalate to deep-think.

## Stage 2 — HYBRID RETRIEVAL (CASCADED, 4 levels)

Even though Triage returns ASK and the pipeline halts there, we document what retrieval *would* find for the bare query, to confirm the ambiguity is real (not an artifact of poor data) and to verify the candidate_chapters Triage proposed are grounded.

### 2.1 — Chapter retrieval (FTS proxy on tariff_lines, since chapter-level cosine wasn't run)

The most direct evidence: which tariff_lines actually have "brake pads" in their description text?

```sql
SELECT code, description, LEFT(code,2) AS chapter
FROM tariff_lines
WHERE to_tsvector('english', description) @@ websearch_to_tsquery('english', 'brake pads');
```

|---|---|---|
| 6813.20.10 | Brake lining and pads | 68 |
| 6813.81.00 | Not containing asbestos : -- Brake linings and pads | 68 |


## Stage 3 — RULES FILTER (programmatic, no LLM)

Not executed in this case. The pipeline does not reach Stage 3 because Triage returned ASK. However, for completeness:

```sql
SELECT source_chapter, excluded_product_text, redirects_to_chapter, redirects_to_heading
FROM chapter_exclusions
WHERE to_tsvector('english', excluded_product_text) @@ websearch_to_tsquery('english', 'brake');
```

Real result: `[]` (no rows). No exclusion rule directly mentions "brake".

Broadening to `friction`:

```sql
SELECT source_chapter, excluded_product_text, redirects_to_chapter, redirects_to_heading
FROM chapter_exclusions
WHERE to_tsvector('english', excluded_product_text) @@ websearch_to_tsquery('english', 'friction');
```

Real result:

| source_chapter | excluded_product_text | redirects_to_chapter | redirects_to_heading |
|---|---|---|---|
| 60 | other asbestos products (friction material) | 68 | 6813 |
| 61 | other asbestos products (friction material) | 68 | 6813 |

These are Ch.60/61 textile exclusions redirecting asbestos friction articles to 6813. Not directly applicable here (we are not in Ch.60/61), but they confirm 6813 is the standing sink for friction articles when they are NOT identifiable as a specific machine part.

No exclusion rule disambiguates 68 vs 87 for brake pads. The 68-vs-87 boundary is governed by **Ch.87 Note 2** (positive scope), not a chapter_exclusions row. This is a known structural gap in the rules-engine: when the deciding evidence is a Chapter Note rather than a "Ch.X does not cover Y" exclusion, the Rules Filter cannot do the work — it has to fall through to the Select LLM with the chapter note injected.

## Stage 5 — VERIFY (V1, rubber-stamp)

V1 = adversarial Gemini-Verify sees `{query: "brake pads", triage_decision: "ASK", clarifying_question: {…}}` and is asked: "would you agree this query is genuinely under-specified and the MCQ options correctly span the disambiguation surface?"

Expected V1 output:

```json
{
  "agree": true,
  "disagree_reason": null
}
```

Rationale: rubber-stamp Verify on an ASK decision is a low-bar check. The 5 MCQ options (motor_vehicle / motorcycle_bicycle / industrial_machinery / friction_material_only / other) together cover the entire HS disambiguation space for brake pads. Gemini-Verify, looking at only the question and not running retrieval, cannot find a sixth plausible classification. It rubber-stamps.

A subtle gap V1 might miss: railway brake parts (Ch.86, heading 8607). If the user means "brake pads for a train", the MCQ has no exact bucket — they'd pick "industrial_machinery" or "other", both of which lead to a follow-on question. This is a **minor MCQ-coverage gap** but not a Verify-stage failure per se. Noted as `data_dependency` below.

V1 verdict: **AGREES**. No escalation.

## Anomalies observed

1. **Legacy rule `vehicle_parts_function` (chapter-rules.ts:113-145) would force-route this query to Ch.87 on the keyword `brake` alone.** This is the exact spurious-keyword routing bug Phase 3 is removing. The Phase 3 Triage LLM correctly suppresses Ch.87 commitment until *intended_use* evidence appears in the query. Worth flagging in the Phase 4 rebuild brief: the new Triage must NOT inherit the legacy rule set's friction-word → vehicle-chapter shortcut.

2. **MCQ option `other` is a soft-escape valve.** If the user clicks it, we have nowhere to go — the pipeline either REFUSES or burns its Q-budget. Consider replacing `other` with a free-text "describe end-use" field (text input) that round-trips through Triage on the next turn. Future design question.

3. **Railway brake parts (Ch.86) are not in the MCQ.** If a user means train brake pads, the MCQ steers them wrong. Either add a 6th option ("Part for a railway/tramway vehicle") or accept the small miss-rate. Low-priority for v1.

4. **The 68-vs-87 boundary is governed by a Chapter Note (Ch.87 Note 2), not a chapter_exclusions row.** Rules Filter cannot do this work. Select-LLM must receive the note text in its context. Confirms that injecting chapter notes into the Select prompt (already designed) is load-bearing for this class of case.
