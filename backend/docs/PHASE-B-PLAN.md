# Phase B Backend Plan - UPDATED (post senior re-audit)

## What changed (and why)

The audit converged on ONE structural change and a set of correctness hardenings. I accepted the convergent core and resolved the simplicity-vs-robustness conflict explicitly.

THE BIG DELTA â€” reorder so the launch ships INLINE-V2 SYNC, and DEFER the async/job/SSE spine entirely. All four lenses (distributed-systems, simplicity, ops-security, founder) independently reached this. WHY: at a single Railway replica + free-tier caps (5 RPM / 20 RPD on gemini-3.5-flash, one classify = 4-7 Flash calls = ~3-4 classifications/DAY), there is no concurrency to absorb, no burst to smooth, no backpressure to manage. The inline path (classify.ts:122-146) is BUILT, rollback-safe (flag default OFF = legacy byte-identical, verified), races an 80s timeout, maps via mapV2Result, and 503s on timeout/system_error. It already delivers the full product value (top-3 + cited rationale + confidence band). The async spine, by contrast, carries a live-DB migration + TWO confirmed production bugs + the single largest net-new chunk (onEvent emitter through recordLayer + ClassifyOptions + worker progress wiring + a new SSE endpoint) + at least four UNbuilt correctness holes the distributed-systems lens surfaced (no reaper, undefined delivery semantics, no graceful drain, inverted retry semantics). Building the durable spine first spends the biggest, riskiest chunk on traffic that does not exist. The draft sequenced STEP 1 (apply migration to PROD) and STEP 2 (async progress plumbing) BEFORE STEP 3 (the inline cutover that actually makes the site work) â€” that is backwards.

RESOLVING THE SIMPLICITY-vs-ROBUSTNESS CONFLICT (the core tension): the distributed-systems lens wants the queue HARDENED (reaper, lease, ON CONFLICT, graceful shutdown, constraint-aware tests, delivery semantics) before it ships; the simplicity/founder lenses want the queue CUT from launch ENTIRELY, with its bugs fixed later when the queue is revived. I did NOT average these. I resolved by SCOPE, not by robustness level: both lenses are RIGHT about their own scope. The queue should NOT ship in v1 (simplicity wins the launch-scope question â€” its value is zero at this load), AND when the queue IS revived it must carry every robustness item distributed-systems listed (the dist-sys lens wins the how-to-build-it-correctly question). Concretely: I CUT the queue from the launch critical path (B3 becomes a fully-specified POST-LAUNCH milestone, code stays dormant behind CLASSIFY_ASYNC=off where it costs nothing), AND I HARDENED the B3 spec itself so the revival is correct-by-design rather than a second round of bug-hunting. This is not a compromise that weakens either position â€” it puts each concern where it is load-bearing. The one thing I did NOT defer is fixing the two job bugs IN THE MIGRATION FILE + createJob NOW (status DEFAULT 'queued' and INSERT...ON CONFLICT): these are 3-line edits, they make the dormant code honest, they keep the file from being a known-broken landmine for the next session, and they cost nothing because they touch no live DB and no model. So: queue deferred (simplicity), queue spec hardened including the reaper/lease/delivery-semantics (dist-sys), the two trivial in-file fixes done now (both lenses agree they are cheap and correct).

SSE and polling both require the same absent emitter plumbing and serve one viewer ~8 events over 30-65s; neither earns its cost at this load. INLINE-vs-ASYNC for the FIRST cutover: INLINE-V2 (USE_V2_CLASSIFIER=on, CLASSIFY_ASYNC=off). It is built, HTTP-smoke-validated, instantly rollback-safe, and delivers the full product. Async is NOT ready (depends on two unfixed bugs, no reaper, inverted retry semantics) and its only win â€” durable job + progress â€” is worthless on a shallow single-flight queue. Close this open question now.

PAID-KEY TIMING: Finish ALL free/offline work first (B0, B1a/b/c offline mocks, B4 reserve, B5 contract test), THEN provision ONE small Tier-1 budget with a HARD Google-console spending cap as the single paid checkpoint to unblock the B1 live smoke + the B2 product-eyeball together. ALTERNATIVES CAP: Exactly 'up to 3, never padded' â€” drop the leaf, keep model order, never invent entries to reach 3. It matches the literal product promise and the eval's top-3 metric; surfacing all resolvable siblings dilutes the cited-rationale UX. One-line slice in the adapter.

## Residual risks

- 80s held HTTP connection: inline-sync holds the request up to 80s. Vercel/Railway/browser intermediaries or mobile networks may idle-timeout a 60-80s request before the server responds, surfacing as a generic network error rather than the clean 503. Mitigation: client timeout aligned to ~80s + retry affordance; monitor real p99. If timeouts prove common in the field, that is the actual trigger to revive the async queue.
- Token bucket is best-effort, not a hard cap: it resets to full on process restart and the server-side 5-RPM window is rolling and does NOT reset because our process did. A Railway redeploy or crash-loop mid-minute can burst past the real cap -> 429s; retries compound. GEMINI_RPM=4 headroom + recreate-style (non-overlapping) deploys reduce but do not eliminate this. Confirm Railway's deploy strategy is stop-then-start, not overlapping (old+new = two buckets).
- Single-replica invariant is enforced by config + a boot-time instance-id log, but NOT by code. An accidental autoscale/replica bump silently doubles the rate bucket, the per-IP limiter, and the cost counter with nothing to hard-stop it. The log makes it visible only if someone reads logs.
- Confident-wrongs ship at launch: repair-exhausted best-effort CLASSIFY remains a known confident-wrong source. The honest LOW band is the only launch-day mitigation; until the escalation-to-ASK fast-follow lands, a free tool promising 'calibrated confidence + cited rationale' will occasionally emit a confidently-wrong code. Founder-accepted, but it is the sharpest product-trust risk.
- Cost guardrail is in-app + best-effort: the hard daily ceiling lives in the single Node process (in-memory). It protects against runaway loops but a restart resets the daily counter, and the Google billing budget alert is reactive (after spend), not a hard stop. On a paid key this is materially safer than the May blind-flying state, but it is not an absolute spend cap.
- B3 revival is deferred but the spec depth (reaper/lease/delivery-semantics/graceful-drain/constraint-aware tests) means the queue is a genuine project, not a quick toggle. If traffic forces it sooner than expected, there is build latency before the queue is correct enough to enable.
- Frontend is the true remaining critical path to a LIVE site: B5 freezes the contract but the use-wizard.ts rebuild (responseType:'refused', multi-turn {questionId,answerId}, alternatives) must be planned-with-user and built before hscode.prevyl.com is actually live. Phase B ends at a frozen contract + a planning trigger, not at a live site.
- Embedding quota is un-paced and un-monitored beyond the new cost log: embeddings are a separate quota not gated by the token bucket. If the embedding ceiling is tighter than assumed, back-to-back classifications could 429 on embeds with only reactive retry as defense. The cost log surfaces it after the fact; it does not prevent it.
- 54 tariff_lines have no tariff_line_attributes row: L4/L5 are believed to degrade gracefully (empty TLA block / SKIP), but this was not re-verified this session against the specific leaves â€” a confident-wrong on one of those leaves would be silent.
